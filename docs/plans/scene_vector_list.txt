SCENE VECTOR LIST — THE FEATURE RESEARCH BROUGHT UNDER SPECIFICATION

This list is the work that puts the scene-vector research under a
specification. The project does two things: it collects ArkUI data off a
HarmonyOS device, and it clusters the scenes it finds in that data. What is
decided here is the quality of that collection and that clustering.

Two things make this list what it is, and both were decided in the session
that preceded it. The first: there are no scene classes, and three attempts
at one were deleted — a C enum of twenty, a PowerShell classifier of
twenty-three, a naming function of twenty-eight shapes. The clustering is
not here to confirm a class list; it is given the vectors and nothing else.
The second: the spec graph is empty over 3,298 lines of tracked code, so
the governance adopted in 2da1e4d has nothing to verify with. Every item
below exists to close one of those two gaps or to repair something the
audits found while looking.

Each item is one skill execution, run in the order below.

- /cb-audit executions read and report; they change nothing.
- /cb-fix executions repair a defect against a reproduction.
- /cb-free sessions bring each finding to the human, one at a time, and
  write the decision into THE DECISIONS IN FORCE of this list.
- /cb-green executions author spec nodes and change code.

Every item ends by bringing this list to the state its work leaves, in the
same session, before the gate is cleared:
- the item is deleted, with its line under What remains, and its prompt;
- each record of THE DECISIONS IN FORCE the item applies is written again to
  what is still to do, its "Applied by" line naming only the items left, and
  deleted when no item is left;
- each finding the item reports and does not resolve is written as an open
  point of the record it bears on when it is a question for the human, and
  as an item in its place in the order, with its prompt, when it is work;
- each name the item wrote differently from the record is written into the
  record and into every later item that cites it, in the form the item
  wrote;
- every reference in the list to the deleted item, or to a name it changed,
  is written again or removed.
An audit cannot write; the list update an audit owes is done by the /cb-free
session after it, which names it in its report.

An item pushes before its gate is cleared. Authoring happens on the VM and
the list is read on the capture machine, so a committed-but-unpushed update
leaves the next item to be chosen from a list that is behind the work. That
happened once: the first item was executed, deleted from this list, and
committed, and because nothing was pushed the same item was read and run a
second time against a graph that already held its nodes. The item is not
finished when the list is written; it is finished when the list the human
reads says so.

Every prompt carries a Spec work section naming its specification work node
by node: each node it adds (id, kind, module, and every edge it carries),
each node it modifies (id and the fields written), each node and each edge
it removes. An item that changes no node says so and gives the reason. The
names a prompt gives are record 4's; the human confirms them before the
envelope is written.

Every prompt carries the BOUNDARY clause: combobul and ArkUI are two
projects, and no rule, kind, check or store of one is carried to the other.

An item runs, at its end, the checks that read the files it changed, and
names them in its report: `npm run spec:check`, and the pipeline on a real
capture where its change reaches the pipeline.

A measurement that an item claims is verified is verified in that session,
against a real capture, and the figures are written into the report. A
figure carried from an earlier session is marked as such.

The captures carry no weight on the design: they are two sessions of one
device held by one person, and nothing in this list treats a number taken
from them as settled beyond the capture it came from. Captures live on the
capture machine and never in this repository — they are pictures of a real
phone in real use.

The baseline the executions read (read each file in full):
- README.md, tools/README.md, tools/cluster/README.md — what the project is
  and what each stage does.
- tools/cluster/rs_extract.py (404 lines), rs_pattern.py (795),
  vectors_build.py (209), vectors_page.py (137) — the measurement.
- tools/rs_capture.ps1 (424) — the device side.
- CLAUDE.md — the governance in force.
- .combobul/runs/audit-spec-genesis/contract.json and
  .combobul/runs/audit-subfeature-spec/contract.json — the two audits this
  list carries out, findings F1–F9 and S1–S11 with their classifications.

       * This project collects ArkUI data and clusters the scenes in it.
         That is the whole of it.
       * Nothing else goes in: no measurement of anything the device does
         in response to a scene, no joining of a scene to any other series,
         and no code whose reason for existing is a question somebody
         downstream of this data would ask.
       * The test for a proposed item is whether it improves the collection
         or the clustering. If it does not, it does not belong here, and no

       * What exists is a capture, two measured vectors, a clustering and

  2. The two vectors and their column contracts. Decided by the human.
       * The pattern vector — what repeats in the layout, and how much of
         the window it holds. Branches are grouped by a description of
         their subtree, and the group covering the most area wins. Ties
         break on vertical position, never on the nearly-tied area.

           column         transform  weight  measures
           pat1_cover     unit       1.0     share of the window that repeats
           pat1_h         unit       1.0     the item's height, in display heights
           pat1_aspect    logratio   1.0     its width / height

           pat_n_groups   log1p      0.7     how many repeating groups exist

         occlusion. Every node that draws, and every externally composed

           vis_text       unit       1.0     nodes tagged Text

/cb-audit — the surface vector's collapse diagnosed, and what a composition
            can be expected to look like
  - What: why the surface vector collapses towards one axis on this
    capture, and whether it carries information the pattern vector does
    not. Each of the five columns examined over the full capture: its
    distribution, its correlation with the other four, its variance, and
    the scenes at each extreme with their screenshots. The substrate
    against content correlation of about -0.8 traced to its cause — whether
    it is arithmetic (five reals summing to one, with three of them usually
    near zero), a property of the capture (two sessions of one device), or
    a defect in the occlusion walk.
    vis_text is examined specifically: over the 299 scenes now measured it
    reaches 0.312 at most and dominates no scene at all — 0 of 299. A
    text-dominant reading is unreachable, and whether that is the device,
    the capture or the measurement is a finding. vis_glyph never exceeds
    0.006 and is examined for whether it can ever be anything but zero.
    The untyped vis_content bucket is the centre of this audit, because it
    is the largest of the six columns in 131 of 299 scenes — 44 percent,
    the same figure as the clustering's outlier rate and almost certainly
    the same scenes. vis_substrate is largest in another 110, so 81 percent
    of scenes are dominated by a column that names nothing on the display.
    How much of vis_content is nodes absent from the client dump entirely,
    how much is nodes the client dump names with a tag the mapping does not
    cover, and whether the geometry fallback already in the code can split
    it. A scene whose surface is 96 percent "we could not tell" has not
    been measured, and no transform or weight on that column recovers it.
    And the question the vector cannot currently answer: WHAT SHOULD A
    COMPOSITION LOOK LIKE. Not a class list - the expected shape of the
    six columns, derived from the data: which columns carry information and
    which record a failure to identify, what range each occupies on scenes
    where the tags did resolve, and therefore what makes a composition
    well-formed and what makes one unreadable. The answer is the thing the
    surface vector is missing, and without it "fits no cluster" cannot be
    told apart from "was never measured".
    Each finding with its evidence and a recommendation; nothing decided.
  - Read: records 2, 3 and 5; rs_pattern.py's visible_surface, vis_kind,
    mark_kind, TAG_KIND and the slot sets, in full; the full patterns.csv
    of a real capture; a client dump in full, to see what tags the device
    actually emits against what TAG_KIND covers; the page.
  - Spec work: none; an audit changes nothing.
  - BOUNDARY: as above.

  - IMPORTANT: Read every file in full. A grep hit is a pointer, not a finding.
  - IMPORTANT: Every figure is measured in this session against a real capture and written into the report.
  - FORBIDDEN: MULTI-AGENT execution is not allowed. DO NOT SPAWN MULTIPLE AGENTS.

/cb-green — the pattern motif drawn again, from measured medians
  - What: the page shows what a repeating group looks like, not only the
    numbers describing it. feature_motifs.py drew this before deletion in
    4421f9b: schematic() laid cells into a phone-shaped SVG from cols,
    rows, h, aspect and arr, a cell cut off at the bottom edge drawn
    dashed, a stack drawn as an offset outline. That function is recovered
    from git history and is the starting point.
    What is NOT recovered is the DESC table beside it - 13 names with prose
    for each, part of the 28-shape taxonomy deleted with it. The drawing is
