SCENE VECTOR LIST — WHAT IS TO BE DONE

The project collects ArkUI data from a HarmonyOS device and describes the
scene on the display. This list holds the work still to be done, in order,
and nothing else. What was done, and why, is in git and in the transcripts.

HOW THE LIST WORKS

- ORDER holds one line per item, in the order they run.
- PROMPTS holds each item's full prompt, starting "/cb-green — <title>" with
  no prefix, ready to paste.
- DEFERRED holds items kept for later, with their prompts. They are not run
  until the human moves them into ORDER.
- Each item is one skill execution.

When an item is finished, in the same session, before its gate is cleared:
- its line is deleted from ORDER and its prompt from PROMPTS;
- every later item it changes is written again to match;
- work it found and did not do is written as a new item in ORDER, with its
  prompt, or as an open point inside the item it belongs to;
- the list is committed, and the push is made through /cb-ops.

RULES FOR EVERY ITEM

- Specification first. Every node an item adds, modifies or removes is
  authored through ril before the code it governs. A removal of an
  invariant is confirmed by the human, node by node, before the envelope.
- No scene classes. A pattern names a structure of components; nothing in
  the repository maps a measurement onto the name of a scene, an app or a
  use.
- Only what is visible on the display enters a feature.
- Terms: the display is the coordinate space every area and fraction is
  measured in; a window is one top-level surface, and several coexist on a
  display; the screen is the physical panel, and is used only for motion.
- Sample timing is read from the capture's samples.csv, never from file
  times.
- Every figure an item reports is measured in that session on a real
  capture. npm run spec:check passes, and the checks that read the changed
  files are run and named.
- Before committing spec work: npm run ril -- journal coalesce.
- BOUNDARY: combobul and ArkUI are two projects. combobul/spec/spec.db holds
  the specification of this project's code, written only through ril. No
  rule, kind, check or store of one is carried to the other.
- The repository lives only on the VM. The capture machine reads it as a
  read-only share and runs the tools from ~\ark_work, where the captures,
  the venv and every output stay. Captures never enter the repository.

The baseline each item reads in full: README.md, tools/README.md, CLAUDE.md,
tools/rs_capture.ps1, tools/cluster/rs_extract.py, rs_scene.py,
rs_pattern.py, vectors_build.py, vectors_page.py, and the checks under
tools/checks/.

/cb-green — motifs from the ArkUI component contracts
  - What: the pattern dictionary becomes a motif dictionary of 21 motifs,
    each derived from an ArkUI component contract and never from a capture,
    and "pattern" is renamed "motif" throughout. A motif absent from a
    capture stays: it reads d = 1, share = 0, count = 0 there.
    SOURCE. Each motif names the contract it comes from - the "Child
    Components" section of the OpenHarmony ArkUI reference
    (docs/en/application-dev/reference/apis-arkui/arkui-ts) - and, where
    the engine builds the component differently, its runtime form in
    arkui_ace_engine (frameworks/core/components_ng/pattern).
    THE 21 MOTIFS.
      repeating containers, the contract names a typed repeated child:
        list       List {List, List/ListItem*}, variant ListItemGroup;
                   contract: only ListItem and ListItemGroup, custom
                   components supported
        grid       Grid {Grid, Grid/GridItem*}; GridItem and custom components
        waterflow  WaterFlow {WaterFlow, WaterFlow/FlowItem*}; FlowItem and
                   custom components
        tabs       Tabs; contract: only TabContent, the tab bar from
                   TabContent's tabBar attribute; runtime (tabs_model_ng
                   InitTabsNode): Tabs/Swiper, Tabs/Divider, Tabs/TabBar,
                   TabContent under the Swiper
        carousel   Swiper {Swiper, Swiper/*}; any children; a Swiper directly
                   under Tabs is the Tabs' own and is not a carousel
        stepper    Stepper {Stepper, Stepper/StepperItem*}; only StepperItem
        menu       Menu {Menu, Menu/MenuItem*}; MenuItem and MenuItemGroup
        grid_row   GridRow {GridRow, GridRow/GridCol*}; GridCol
      fixed-shape containers:
        scroll_page  Scroll, exactly one child
        refresh      Refresh, exactly one child
        sidebar      SideBarContainer, exactly two children
      leaves, the contract allows no children:
        video_large, video_medium, video_small  XComponent and Video, by the
                     size labels
        web          Web
        text_input   TextInput, TextArea, Search
        button       Button
        slider       Slider
        index_bar    AlphabetIndexer
      icon structures, kept from the current dictionary:
        icon_row     Row {Row, Row/icon*}
        icon_grid    composed, as now
    CUSTOM COMPONENTS. A custom component is a CustomNode, which derives
    from UINode and has no render node (custom_node.h), so its root stands
    in its place under the container. On the capture of 2026-10-28 List's
    kept children are Column in 184 scenes and ListItem in 143.
    VECTOR. 21 motifs x (d, share, count) = 63 values, in a fixed order, the
    same on every capture.
    CLUSTERING. All 63 columns on every capture. A constant column changes
    no distance and no PCA component; it is reported, never dropped, so the
    column set is the same on every capture and a scene classified online
    is measured on every motif.
